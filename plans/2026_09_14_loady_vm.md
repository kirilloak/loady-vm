# Loady remote development VM

## Goal

Build `loady-vm`, an Ubuntu Server VM on the Proxmox host that holds the `loady-one` checkout and runs the Loady
backend, frontend and toolchain for JetBrains Rider remote development, with every file that describes or drives it
living in this private repository and nothing of it visible in `loady-one`.

## Success criteria

- `ssh loady-vm` works on the LAN and `ssh loady-vm-ts` works off it.
- Rider (JetBrains Gateway, SSH) opens `/home/dev/loady-one/backend/Loady.slnx` on the VM, indexes, builds, runs a
  test and hits a breakpoint.
- `ld-start` on the VM brings up the containers, builds the solution, seeds, and starts the function hosts;
  `http://localhost:7000` (APIM) and `http://localhost:8080` (frontend) answer in the Mac's browser through
  forwarding.
- `ld-add`, `ld-update`, `ld-remove` run EF migrations against the VM's SQL Server.
- `git -C ~/loady-one status --porcelain` is empty on both machines with the agent instruction files in place, and
  `git -C ~/loady-one diff` shows nothing this work introduced.
- `git -C ~/loady-vm status` is clean after a converge run; every secret is in Bitwarden, none in the repository.
- A destroy + apply rebuilds the machine unattended except for the browser sign-ins listed under Manual actions.

## Blockers

None. Everything needed exists: the Proxmox host, the tailnet, Bitwarden, and a working reference implementation of
the same shape.

## Approach

One Terraform root creates the VM; one convergent `bootstrap.sh` owns everything inside it; one `setup.sh` runs that
bootstrap from the Mac on demand and carries the Mac-only files across. A `ld-*` shell function file, sourced from
`~/.zshrc` on both machines, is the whole command surface. This mirrors a design already proven on this host, which
is why it is chosen over Ansible, cloud-init user-data, or a Dockerised dev container: the failure modes are known.

The three rules that shape every decision below:

1. **`loady-one` is read-only to this setup.** No file is added, edited or committed there. The two things that must
   appear inside that checkout — the agent instruction files and, if ever needed, a compose override — are symlinks
   into `~/loady-vm` plus entries in `.git/info/exclude`, which is local-only and never pushed.
2. **This repository is the only memory.** Anything learned while building it is written here, in the same change.
3. **The VM is disposable.** Nothing on its disk is authoritative except unpushed Git work. Rebuild rather than
   repair.

### Sizing and placement

| Setting | Value | Why |
|---|---|---|
| Node | `pve-2` | the only node with the cores and memory; the existing dev VM lives there too |
| `vm_id` | `201` | `200` is taken |
| Name / hostname | `loady-vm` | the LAN name, the MagicDNS name, and the Proxmox name are one string |
| Address | `192.168.1.51/24` | free, outside the router's DHCP pool, neighbouring the existing VM |
| Cores | `16`, type `host`, `cpu.units = 2048` | the whole host; only one workstation VM runs at a time |
| Memory | `32768`, no balloon | asked for; a Cosmos emulator, SQL Server, thirteen function hosts and a Rider backend indexing a large solution do not fit comfortably in less |
| Disk | `300 GB` raw on `local-zfs`, ext4, discard on | the solution, NuGet, node_modules, SQL and Cosmos data; thin-provisioned, so unused space is not consumed |
| Image | Ubuntu Server LTS cloud image | same family as the existing VM, amd64, matches the deployment targets |

**The two workstation VMs must not run at once.** 32 GB + 32 GB plus the Kubernetes guests overcommits `pve-2`, and
under memory pressure a guest OOM-kills its own build. `ld-up` therefore refuses to start `loady-vm` while the other
workstation VM is running, and names it; `ld-down` stops it cleanly. Enforced in code, not in a sentence.

### Terraform state

Local state in `infra/loady-vm/terraform.tfstate`, gitignored, never committed: it holds the Proxmox password and a
Tailscale auth key in clear. There is no remote backend because introducing one would mean either a new cloud account
and ongoing cost, or reusing an existing project, which is the cross-link this work is meant to avoid. The cost of
losing the state file is one `terraform import` of a single VM, or a rebuild; both are documented in the runbook.

### Secrets

Bitwarden stays the source. `ld-tfin` (a function in `scripts/loady-shell.zsh`) reads `infra/loady-vm/.tf-vars` —
one line per `TF_VAR_*`, giving a Bitwarden item id and a field — exports them, and runs `terraform init`. Three
items feed the root:

| Item | Fields | Used for |
|---|---|---|
| the existing Proxmox item | login password | `root@pam` on the Proxmox API |
| the existing Tailscale item | `api_key`, `tailnet` | minting the VM's one-hour member auth key |
| a new `loady-vm/keys` item | `ssh_loady_vm_base64`, `ssh_loady_vm_ado_base64` | the Mac's key **to** the VM (backup only, stays on the Mac) and the VM's key to Azure DevOps |

`ssh_loady_vm_ado_base64` is a new passphrase-less ed25519 key whose public half is registered once on the Azure
DevOps user profile. It is what lets a headless Rider backend, a tmux session and a cron job push without an agent
forwarded from the Mac. The Mac's own Azure DevOps key is not copied to the VM: one key per machine, so revoking one
does not revoke the other.

### What the bootstrap installs

Resolved at run time rather than pinned, except where a file in `loady-one` owns the line.

| Group | Contents | Source of the version |
|---|---|---|
| Base | `openssh-server`, `ufw`, `unattended-upgrades`, `git` (git-core PPA), `make`, `build-essential`, `python3`, `tmux`, `htop`, `zsh`, `zip`, `lsof` | Ubuntu |
| Docker | `docker-ce`, CLI, buildx, compose plugin; daemon pinned to publish on `127.0.0.1` | Docker apt repo |
| .NET | SDK for the channel in `backend/global.json` (`10.0`), `dotnet-ef` global tool | `dotnet-install.sh` |
| Azure Functions | `azure-functions-core-tools@4` via npm | npm, unpinned |
| Node | Node.js 22 LTS (the major `frontend/CLAUDE.md` requires), `yarn` classic | NodeSource apt repo |
| PowerShell | `pwsh` 7 | Microsoft apt repo |
| Azure | `az` CLI | Microsoft apt repo |
| Tools | `jq`, `rg`, `fd`, `shellcheck`, `gh` | GitHub releases / apt |
| SQL | `sqlcmd` (mssql-tools18) | Microsoft apt repo |
| Agents | `claude` (native installer), `codex`, `bw` (npm) | upstream, unpinned |
| Tailnet | `tailscale`, joined with `--ssh` | Tailscale apt repo |

Azure Functions Core Tools comes from npm rather than the Microsoft apt repo deliberately: the apt package trails
Ubuntu codenames and has repeatedly had no build for the newest release, which would fail the bootstrap on exactly
the image it targets. npm has one package for every platform.

Host tuning is carried over wholesale from the working reference, because the reasons apply identically: `noatime`,
`/tmp` on tmpfs, no guest I/O scheduler, raised inotify and open-file limits (Rider's indexer plus Vite plus
containers exceed the defaults), `mitigations=off`, sshd keys-only with TCP forwarding and SFTP for Gateway, ufw
denying everything but SSH from the LAN and anything on `tailscale0`, unattended security updates.

### Running Loady on Linux

`backend/backend.ps1` is Windows-only in the parts that matter — `taskkill`, `Start-Process` into new windows, and
the Cosmos DB Emulator `.exe`. It is not modified. `scripts/ld-dev.sh` in this repository is the Linux equivalent and
reads `overrides/processes.json`, which lists each function host, its port and its build output directory:

| Function | Port |
|---|---|
| `Loady.Backend.Api` | 7160 |
| `Loady.Events.Api` | 7296 |
| `Loady.Backoffice.Api` | 7001 |
| `Loady.Loady2Go.Api` | 7152 |
| `Loady.Loady2Share.Api` | 7094 |
| `Loady.Public.Api` | 7247 |
| `Loady.Public.BusinessPartners.Api` | 7248 |
| `Loady.Public.Lanes.Api` | 7249 |
| `Loady.Public.Products.Api` | 7250 |
| `Loady.Public.LoadingPoints.Api` | 7253 |
| `Loady.Public.UnloadingPoints.Api` | 7254 |

Each host starts detached with `setsid func start --no-build --port <port>`, its pid and log under
`~/.local/state/loady-vm/run/<name>.{pid,log}`, so `ld-stop` and `ld-logs` address them by name instead of killing
every `func` on the machine. `AZURE_FUNCTIONS_ENVIRONMENT` and `EnvironmentName` are set to `Localhost` in the
profile, as `backend.ps1` does. The public hosts start only with `--public`, matching `-IncludePublic`.

Containers come from `loady-one/backend/compose.yaml` — the tracked file, unchanged — plus
`overrides/backend/compose.linux.yaml` in this repository, which adds only the Cosmos emulator service. Compose is
invoked with `--project-directory ~/loady-one/backend` so the `./nginx.conf` bind mount still resolves. Nothing needs
a port binding rewrite: the Docker daemon on the VM publishes to `127.0.0.1` for every container.

### Command surface

`scripts/loady-shell.zsh`, sourced from `~/.zprofile` and `~/.zshrc` on the Mac and on the VM. Every function runs a
tracked script from this repository, so the Mac and the VM run the same code. The four existing `ld-*` aliases in
`~/.zshrc` are deleted as part of this work — they point at `~/Repositories/loady/loady-one`, a path that no longer
exists, so all four are currently broken.

| Command | What it does | Where it runs |
|---|---|---|
| `ld-vm <cmd>` | runs a command in the VM's login shell from `~/loady-one` | Mac |
| `ld-vm-setup [--files-only]` | converges the VM: bootstrap plus the Mac-only files | Mac |
| `ld-tfin` | loads `.tf-vars` from Bitwarden, then `terraform init` | Mac |
| `ld-tfd [--force]` | destroy and recreate; refuses while the VM holds unpushed work | Mac |
| `ld-up` / `ld-down` | power the VM on/off through the Proxmox API; `ld-up` refuses while the other workstation VM runs | Mac |
| `ld-reset` | `compose down -v`, `pull`, `up -d`; `--hard` also `dotnet clean` and clears the run state | VM |
| `ld-start [--public]` | containers, build, seed, function hosts | VM |
| `ld-stop` / `ld-status` / `ld-logs <name>` | the function hosts and the containers | VM |
| `ld-build` / `ld-seed` | the solution; the two seeders | VM |
| `ld-fe [company] [user]` | `yarn install --frozen-lockfile` then `yarn start` with the local-mode env | VM |
| `ld-add <name>` / `ld-update` / `ld-remove` | EF migrations in `src/Shared/Loady.Relational.Infrastructure` | VM |
| `ld-agents` | relinks the agent instruction files and refreshes `.git/info/exclude` | both |

`ld-add`/`ld-update`/`ld-remove` replace the broken aliases and pass the connection string explicitly
(`-- --connection ...`) rather than relying on an exported shell variable, so they behave the same in an agent's
non-interactive shell.

### Agent instruction files

`LOADY.md` and `LOADY-INFRA.md` under `~/Repositories/kirill/settings/macos/agents/` are the only surviving copies of
the Loady instruction files: the current `~/loady-one` checkout has no `CLAUDE.md` at all. They move here and become
canonical:

```
agents/backend/CLAUDE.md     <- LOADY.md
agents/infrastructure/CLAUDE.md <- LOADY-INFRA.md
```

`scripts/link-agent-files.sh` (`ld-agents`) symlinks `~/loady-one/backend/CLAUDE.md` and
`~/loady-one/backend/AGENTS.md` at `agents/backend/CLAUDE.md`, and appends `/backend/CLAUDE.md`, `/backend/AGENTS.md`
and `/backend/plans/` to `~/loady-one/.git/info/exclude` if absent. An edit an agent makes through the symlink lands
in this repository, which is where it belongs. The launchd watcher and its two- and three-way sync rules are
retired: with one owner and symlinks there is nothing to reconcile, and a bidirectional newest-wins sync is a way to
lose an edit.

`agents/backend/CLAUDE.md` says ".NET 9" while `backend/global.json` pins `10.0.100`. Correcting it is a one-line
edit and is in scope for the move, since the file is being rewritten anyway.

### Rider

JetBrains Gateway, SSH connection to host `loady-vm`, project `/home/dev/loady-one/backend/Loady.slnx`. Forwarded
ports, all on the VM's loopback:

| Port | What | When |
|---|---|---|
| `8080` | frontend dev server | always |
| `7000` | APIM (nginx) — what the frontend calls | always |
| `7160`, `7296` | Backend and Events function hosts | always |
| `1433` | SQL Server | Mac-side database clients |
| `6379` | Redis | Mac-side clients |
| `8081`, `1234` | Cosmos emulator and its explorer | when inspecting documents |
| `10000`-`10002` | Azurite blob/queue/table | when using Azure Storage Explorer |
| `7001`, `7152`, `7094` | Backoffice, Loady2Go, Loady2Share | when working on those |
| `7247`-`7254` | public APIs | when testing the public surface |

Rider's **Settings → Version Control → Git → Use credential helper** does not apply here: Git to Azure DevOps goes
over SSH with the VM's own key, bound per checkout with `core.sshCommand`, so nothing prompts.

## Steps

Steps 1-11 build the repository; 12-16 create and verify the machine. Each is verifiable on its own.

1. **Repository skeleton.** `AGENTS.md` (instruction ownership, authorization, working rules, all written for this
   repository alone), `CLAUDE.md` containing only `@AGENTS.md`, `README.md`, `.gitignore` (`.terraform/`,
   `*.tfstate*`, `.tf-vars` stays tracked — it holds ids, not secrets).
   *Verify:* `git status` clean after commit; no occurrence of any other project's name in any file.

2. **Move the agent instruction files.** `agents/backend/CLAUDE.md` and `agents/infrastructure/CLAUDE.md` from the
   two files under `~/Repositories/kirill/settings/macos/agents/`, with the .NET version corrected.
   *Depends on:* 1. *Verify:* both files present and non-empty; content diff against the originals is only the
   version correction.

3. **`scripts/link-agent-files.sh`.** Symlinks into `~/loady-one/backend/`, `.git/info/exclude` entries, idempotent,
   refuses to overwrite a real file it did not create.
   *Depends on:* 2. *Verify:* run it, then `git -C ~/loady-one status --porcelain` is empty and
   `readlink ~/loady-one/backend/CLAUDE.md` points into `~/loady-vm`; run it twice and the exclude file gains
   nothing the second time.

4. **`scripts/loady-shell.zsh`.** Every `ld-*` function from the table, each delegating to a tracked script. Modelled
   on the existing workstation shell file, including the rule that no helper function name starts with an underscore
   — an agent's shell snapshot drops those and every command that uses one dies with "command not found".
   *Depends on:* 1. *Verify:* `zsh -n` parses it; sourcing it in a fresh shell defines every documented function.

5. **`infra/loady-vm/` Terraform root.** `versions.tf` (Terraform ~> 1.16, `bpg/proxmox`, `tailscale/tailscale`),
   `provider.tf`, `variables.tf` with the sizing table's defaults, `main.tf` (image download, VM, single-use
   Tailscale key, a `terraform_data` that removes stale tailnet registrations before create and on destroy, and a
   `terraform_data` that runs the bootstrap over SSH on every apply), `outputs.tf`, `.tf-vars`, and a local backend.
   *Depends on:* 1. *Verify:* `terraform fmt -check` and `terraform validate` pass; `terraform plan` after
   `ld-tfin` shows exactly the VM, the image, the key and the two `terraform_data` resources.

6. **`infra/loady-vm/tailscale-api.sh`.** Deletes exact-hostname `loady-vm` registrations through the Tailscale API
   and confirms the tailnet is clear before returning, so a rebuilt VM does not come back as `loady-vm-1`.
   *Depends on:* 5. *Verify:* run with the key loaded against the live tailnet while no such device exists — it
   lists devices and exits 0.

7. **`infra/loady-vm/bootstrap.sh`.** The whole guest, in the order of the table above, convergent and safe to rerun,
   streaming progress to its caller and to a 0600 log under `~/.local/state/loady-vm/bootstrap/` with a stable
   `latest.log` symlink. Ends with a version table and reboots on a 15-second timer when Ubuntu asks.
   *Depends on:* 5. *Verify:* `shellcheck` and `bash -n` clean; then step 13 is the real test.

8. **Checkout and warm-up inside the bootstrap.** Place the Azure DevOps key, pin `ssh.dev.azure.com`'s host keys
   against Microsoft's published fingerprints, clone `loady-one` to `~/loady-one`, bind it to that key with
   `core.sshCommand`, then `dotnet restore` + `build` the solution, `yarn install --frozen-lockfile` in `frontend/`,
   and `docker compose pull` — so Rider opens onto a warm cache and the first run is not a download. A checkout with
   uncommitted work is reported and left alone, never pulled.
   *Depends on:* 7. *Verify:* part of step 13.

9. **`infra/loady-vm/setup.sh`.** Runs the bootstrap over SSH with the Bitwarden-loaded register, then carries the
   Mac-only files: `~/loady-one/.claude/settings.local.json` (gitignored there) and anything else found to be
   gitignored-but-needed during step 13. `--files-only` skips the bootstrap.
   *Depends on:* 7. *Verify:* `--files-only` against the built VM copies the files and reports what it skipped.

10. **`scripts/ld-dev.sh` and `overrides/processes.json`.** The function-host runner: `start`, `stop`, `status`,
    `logs`, `restart`, honouring `--public`, with pid/log files per host and a readiness wait on the Cosmos emulator
    before seeding.
    *Depends on:* 4. *Verify:* on the VM, `ld-start` then `ld-status` shows every host listening; `ld-stop` leaves no
    `func` process; `ld-logs Loady.Backend.Api` prints that host's log.

11. **`overrides/backend/compose.linux.yaml`, `scripts/ld-reset.sh`, `scripts/ld-migrate.sh`.** The Cosmos service
    override, the container reset, and the three EF migration entry points.
    *Depends on:* 4. *Verify:* `docker compose -f ... config` resolves with the override; `ld-update` applies
    migrations against the VM's SQL Server.

12. **Docs.** `docs/remote-development.md` (architecture, what runs where, the Rider procedure, the port table, access
    boundaries, the two-VMs-not-at-once rule), `docs/manual-secrets.md` (the Bitwarden register and how to restore
    it), `infra/loady-vm/README.md` (install, operate, lost access, rebuild — the ordered runbook).
    *Depends on:* 1-11. *Verify:* a reader who has only this repository can build the machine from zero.

13. **Create the VM.** Generate the Mac→VM key and the Azure DevOps key, back both up to Bitwarden, register the
    public half of the ADO key on the Azure DevOps profile, add `192.168.1.51 loady-vm` to `/etc/hosts` and the two
    `Host` blocks to `~/.ssh/config`, reserve the address on the router, then `ld-tfin && terraform apply`.
    *Depends on:* 5-9. *Verify:* the apply ends with the bootstrap's version table; `ssh loady-vm true` succeeds.

14. **Accounts on the VM.** `ld-vm bw login`, `ld-vm 'az login'`, `ld-vm claude`, `ld-vm codex` — each a device or
    browser flow that cannot be handed over as a token.
    *Depends on:* 13. *Verify:* each reports signed in.

15. **Run Loady end to end on the VM.** `ld-reset`, `ld-start`, `ld-fe`, then the frontend and the APIM endpoint in
    the Mac's browser through forwarding; one EF migration applied and rolled back.
    *Depends on:* 10, 11, 13. *Verify:* the success criteria list, line by line.

16. **Connect Rider and cut over.** Gateway SSH connection, the forwarded port set, indexing, a build, a test run, a
    breakpoint, a commit and a push from the VM. Then remove the four dead `ld-*` aliases from `~/.zshrc` and add the
    source line for `scripts/loady-shell.zsh` to `~/.zprofile` and `~/.zshrc`; retire the launchd agent watcher.
    *Depends on:* 13-15. *Verify:* every success criterion holds; `launchctl list | grep watch-agents` is empty.

## Assumptions

- The Proxmox host, its `root@pam` credential, the `local-zfs` datastore and `vmbr0` are unchanged from how the
  existing workstation VM uses them.
- `192.168.1.51` and `vm_id` 201 are free. Checked against the existing root's defaults, not against the live host —
  step 13 confirms before creating.
- The same personal tailnet is used; `loady-vm` joins as a member device, so the existing policy that lets the
  founder reach their own devices already covers it.
- `loady-one` builds and runs on Linux amd64. The solution targets `net10.0` and the containers are all Linux
  images, including the Cosmos emulator's `vnext` build; the only Windows dependencies found are inside
  `backend.ps1`, which is replaced rather than run.
- The company's Azure DevOps allows an additional SSH public key on the user profile.

## Risks

- **The Cosmos emulator `vnext` image is the least predictable dependency.** It is the one service with no
  supported-on-Linux history behind it in this setup, and its startup is slow enough that seeding races it. Mitigated
  by an explicit readiness wait before seeding and by keeping its data in a named volume so a restart is not a
  reseed. If it proves unusable, the fallback is the real Cosmos DB free tier, which is a configuration change in
  `local.settings.json` overrides, not a redesign.
- **Both workstation VMs running at once overcommits the host.** Mitigated in code: `ld-up` refuses and names the
  other VM. It cannot be enforced for a start from the Proxmox web UI.
- **Company source on personal hardware.** The VM holds a full `loady-one` checkout on a home Proxmox host. Disk is
  not encrypted at rest, the guest has no password login, and the only inbound paths are SSH from the LAN and the
  tailnet. Whether that meets the employer's expectations is a founder decision, not a technical one, and it is worth
  settling before step 13 rather than after.
- **Two machines drift.** The Mac keeps a `loady-one` checkout as a fallback. It is not synchronised with the VM and
  must not become a second live workspace; Git remotes are the only transfer boundary.
- **The agent instruction files exist in exactly one copy right now.** Step 2 moves them; until that commit is
  pushed, a mistake loses them. Copy, verify, commit, then delete the originals — in that order.

## Decisions needed

1. **Company source on personal hardware** — the risk above. Proceed, or stop at step 12 with the repository built
   and the machine uncreated.
2. **Disk size.** 300 GB proposed. Thin-provisioned, so the only cost of going larger is the ZFS pool's headroom
   against the other guests.
3. **Whether `ld-up`/`ld-down` should also stop the other workstation VM** rather than refusing. Refusing is
   proposed: stopping a machine that might be running a build is not a thing a convenience command should decide.
