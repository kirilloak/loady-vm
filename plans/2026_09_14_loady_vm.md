# Loady remote development VM

## Goal

Build `loady-vm`, an Ubuntu Server VM on the Proxmox host that holds the `loady-one` checkout and runs the Loady
backend, frontend and toolchain for JetBrains Rider remote development, with every file that describes or drives it
living in this private repository and nothing of it visible in `loady-one`.

## Success criteria

- `ssh loady-vm` works on the LAN and `ssh loady-vm-ts` works off it.
- Rider (JetBrains Gateway, SSH) opens `/home/dev/loady-one/backend/Loady.slnx` on the VM, indexes, builds, runs a
  test and hits a breakpoint.
- `ld-start` on the VM brings up the containers, builds, seeds, and starts the eleven function hosts.
- **The full request path works through the container**: the frontend at `http://localhost:8080` in the Mac's
  browser calls `http://localhost:7000/app/...`, nginx in the `apim` container reaches the function host on the VM's
  host interface, and the response renders. This is the one criterion that proves the Linux-specific work in this
  plan; everything else would pass on a machine where it is still broken.
- `ld-add`, `ld-update`, `ld-remove` run EF migrations against the VM's SQL Server.
- `git -C ~/loady-one status --porcelain` is empty on the VM with the agent instruction files in place, and
  `git -C ~/loady-one push` to Azure DevOps succeeds from a headless session with no prompt and no forwarded agent.
- Every secret is in Bitwarden; `rg` over this repository finds no key, password or token.
- A destroy + apply rebuilds the machine unattended except for the browser sign-ins in step 18.
- `ld-*` commands resolve on the VM in a non-interactive agent shell, not only in an interactive one.
- Two worktrees exist at once, both build, and the second `ld-start` is refused by name rather than colliding on
  port 1433.

## Blockers

None. Everything needed exists: the Proxmox host, the tailnet, Bitwarden, the Azure DevOps key, and a working
reference implementation of the same shape on the same host.

## Approach

One Terraform root creates the VM; one convergent `bootstrap.sh` owns everything inside it; one `setup.sh` runs that
bootstrap from the Mac on demand, between applies. A `dotfiles/` folder with its own sync owns the agent and Rider
configuration on the VM, so nothing has to be copied from the Mac at all. A `ld-*` shell function file, sourced from
`~/.zshrc` on both machines, is the whole command surface. This mirrors a design already proven on this host, which
is why it is chosen over Ansible, cloud-init user-data, or a dev container: the failure modes are known.

The five rules that shape every decision below:

1. **`loady-one` is read-only to this setup.** No file is added, edited or committed there. The two things that must
   appear inside that checkout — the agent instruction files — are symlinks into `~/loady-vm` plus entries in
   `.git/info/exclude`, which is local-only and never pushed.
2. **Git is manual.** No script and no agent commits, pushes, merges, opens a pull request, or creates a branch in
   either repository. Work ends in the working tree, and the founder commits it. An agent finishing a task offers a
   short suggested commit message as text and stops there. This is a rule of this repository, written into its
   `AGENTS.md`, not a convention to be inferred.
3. **Azure DevOps over SSH, and no GitHub CLI.** Loady's remote is `git@ssh.dev.azure.com`. Nothing in this setup
   installs or calls `gh`; GitHub is reached only as an SSH Git remote for this repository itself.
4. **The Mac is a client, plus a cold fallback.** After cut-over it runs Rider's client, a browser, `ssh`, and the
   Terraform root that owns the VM. It keeps `~/loady-vm`, and it keeps `~/loady-one` as an emergency fallback for
   when the Proxmox host is down — not as a second live workspace. Nothing synchronises the two checkouts: Git
   remotes are the only transfer boundary, and a fallback session ends by pushing.
5. **The VM is disposable — but its working tree is not.** Nothing on its disk is authoritative except uncommitted
   and unpushed Git work, and under rule 2 that is the normal state rather than an exception. `ld-tfd` refuses to
   destroy the VM while any exists, and `--force` is the only way past it.

### Sizing and placement

| Setting | Value | Why |
|---|---|---|
| Node | `pve-2` | the only node with the cores and memory; the existing dev VM lives there too |
| `vm_id` | `201` | `200` is taken |
| Name / hostname | `loady-vm` | the LAN name, the MagicDNS name, and the Proxmox name are one string |
| Address | `192.168.1.51/24` | free, outside the router's DHCP pool, neighbouring the existing VM |
| Cores | `16`, type `host`, `cpu.units = 2048` | the whole host; only one workstation VM runs at a time |
| Memory | `32768`, no balloon | a Cosmos emulator, SQL Server, eleven function hosts and a Rider backend indexing a large solution |
| Disk | `300 GB` raw on `local-zfs`, ext4, discard on | solution, NuGet, node_modules, SQL and Cosmos data; thin-provisioned |
| Image | Ubuntu Server cloud image, codename chosen in step 5 | see below — the codename is a dependency, not a detail |

**The two workstation VMs must not run at once.** 32 GB + 32 GB plus the Kubernetes guests overcommits `pve-2`, and
under memory pressure a guest OOM-kills its own build. `ld-up` therefore refuses to start `loady-vm` while the other
workstation VM is running, names it, and prints the one command that resolves it: `ld-up --takeover`, which sends
that VM a graceful ACPI shutdown, waits for it to actually stop, and only then starts this one. Refusing by default
is right because the other machine may be mid-build and a silent shutdown would lose it; making the override one
flag is right because the answer is nearly always "yes, switch me over" and a rule that costs three manual steps
gets routed around. `ld-down` stops this VM the same graceful way. Enforced in code, not in a sentence.

**The Ubuntu codename gates one package.** Azure CLI comes from `packages.microsoft.com/repos/azure-cli/` keyed by
codename, and a cloud image whose codename that repository has not published yet fails the bootstrap on exactly the
image it targets. Step 5 checks before the image is chosen and falls back to the current LTS image. The other
Microsoft-published tools are avoided rather than gated — see the install table.

### Terraform state

Local state in `infra/loady-vm/terraform.tfstate`, gitignored, never committed: it holds the Proxmox password and a
Tailscale auth key in clear. There is no remote backend because introducing one would mean either a new cloud account
and ongoing cost, or reusing an existing project, which is the cross-link this work is meant to avoid. The cost of
losing the state file is one `terraform import` of a single VM, or a rebuild; both are documented in the runbook.

### Secrets and identities

Bitwarden stays the source. `ld-tfin` (a function in `scripts/loady-shell.zsh`) reads `infra/loady-vm/.tf-vars` —
one line per `TF_VAR_*`, giving a Bitwarden item id and a field — exports them, and runs `terraform init`. Three
items feed the root:

| Item | Fields | Used for |
|---|---|---|
| the existing Proxmox item | login password | `root@pam` on the Proxmox API |
| the existing Tailscale item | `api_key`, `tailnet` | minting the VM's one-hour member auth key |
| a new `loady-vm/keys` item | `ssh_loady_vm_base64`, `ssh_loady_ado_base64`, `ssh_loady_vm_github_base64` | the Mac's key **to** the VM (backup only, it stays on the Mac); the Azure DevOps key with its passphrase removed; the VM's key to GitHub |

**The Azure DevOps key is the existing `~/.ssh/loady/id_rsa`, carried to the VM with its passphrase removed** —
settled, because the requirement is that the key is copied to the VM and git then works there with no UI and no
ceremony, only SSH.

Copying it is the easy half. The passphrase is the half that decides the design: the key file is encrypted
(`aes256-ctr`), and an encrypted key cannot be used unattended. A headless Rider backend, a `ld-vm git push`, a tmux
session or anything an agent runs would each need an `ssh-agent` primed by hand after every reboot, which is the
opposite of flawless. So the copy that goes to Bitwarden and onto the VM is passphrase-less (`ssh-keygen -p -N ""`
on a **copy**, never in place); the original on the Mac keeps its passphrase for fallback use.

Reusing this key rather than generating a second one also means no Azure DevOps web UI at any point — the key is
already registered on the profile. It is RSA 3072, which matters: RSA is what Azure DevOps accepts for Git over SSH,
so a freshly generated ed25519 key would register and then fail every push, a confusing thing to debug on a headless
machine. The cost is one identity for two machines — revoking it revokes both — which is acceptable because the Mac
is now a fallback rather than a daily pusher.

**The GitHub key** is a new ed25519 key whose only job is cloning this repository onto the VM. That clone is a hard
dependency of everything after the bootstrap: without `~/loady-vm` on the VM there is no `loady-shell.zsh`, so no
`ld-*` command exists there. GitHub's host keys are pinned from `https://api.github.com/meta` with `curl` — an HTTPS
request, not a CLI — with the published fingerprints as the fallback if it is unreachable.

**Git identities are per checkout.** The bootstrap sets `user.name = Kirill Starodubtsev` and
`user.email = kirill.starodubtsev@loady.com` with `git -C ~/loady-one config`, and the founder's GitHub identity
globally for this repository's own commits. The work address is never set globally: it would sign commits here with
it too.

Resolved at run time rather than pinned, except where a file in `loady-one` owns the line.

| Group | Contents | Source |
|---|---|---|
| Base | `openssh-server`, `ufw`, `unattended-upgrades`, `git` (git-core PPA), `make`, `build-essential`, `python3`, `tmux`, `htop`, `zsh`, `zip`, `lsof`, `ca-certificates` | Ubuntu |
| Docker | `docker-ce`, CLI, buildx, compose plugin; daemon publishing on `127.0.0.1` | Docker apt repo |
| .NET | SDK for the channel in `backend/global.json` (`10.0`), `dotnet-ef` global tool | `dotnet-install.sh` |
| Azure Functions | `azure-functions-core-tools@4` | npm |
| Node | Node.js 22 LTS (the major `frontend/CLAUDE.md` requires), `yarn` classic | NodeSource apt repo |
| Azure | `az` CLI | Microsoft apt repo, codename-gated |
| Tools | `jq`, `rg`, `fd`, `shellcheck`, `go-sqlcmd` | GitHub releases / apt |
| Agents | `claude` (native installer), `codex`, `bw` | upstream, unpinned |
| Tailnet | `tailscale`, joined with `--ssh` | Tailscale apt repo |

Four deliberate departures from the obvious choice:

- **No `gh`.** Rule 3. The reference implementation this plan borrows from uses it for host-key pinning and
  credential help; neither applies here, and installing a GitHub CLI on a machine whose work remote is Azure DevOps
  invites an agent to reach for it.
- **Functions Core Tools from npm, not apt.** The `packages.microsoft.com/.../prod` apt package trails Ubuntu
  releases badly and has repeatedly had no build for the newest one. npm has one package for every platform.
- **`go-sqlcmd` from its GitHub release, not `mssql-tools18`.** Same repository, same problem; `go-sqlcmd` is a
  single static binary with no repository to be absent from.
- **No PowerShell.** `frontend.ps1` only exports four variables and runs `yarn`, and `ld-fe` replaces it;
  `backend.ps1` is replaced wholesale. Installing `pwsh` would add another codename-gated Microsoft dependency for
  nothing. If it is ever wanted, `dotnet tool install --global PowerShell` installs it from NuGet — a line in the
  runbook, not in the bootstrap.

Host tuning is carried over wholesale from the working reference, because the reasons apply identically: `noatime`,
`/tmp` on tmpfs, no guest I/O scheduler, raised inotify and open-file limits (Rider's indexer plus the dev server
plus containers exceed the defaults), `mitigations=off`, sshd keys-only with TCP forwarding and SFTP for Gateway,
unattended security updates, and ufw denying everything inbound but SSH from the LAN and anything on `tailscale0` —
with one addition this setup needs and the reference does not, in the next section.

### The two Linux-only defects, and their fixes

Both are invisible on macOS and Windows, and both break the same path: browser → frontend → `apim` container →
function host on the VM. Neither is fixed by editing `loady-one`.

1. **`backend/nginx.conf` proxies to `host.docker.internal`.** Docker Desktop provides that name; Docker Engine on
   Linux does not, and nginx fails to resolve it at startup. Fixed in this repository's compose file with
   `extra_hosts: ["host.docker.internal:host-gateway"]` on the `apim` service, which makes the name resolve to the
   bridge gateway. The `nginx.conf` itself is bind-mounted read-only straight from `~/loady-one/backend/nginx.conf`,
   so the team's routing changes are picked up without a copy to maintain.
2. **ufw's default deny blocks the container reaching back to the host.** Traffic from the compose bridge to the
   function ports arrives inbound on a `br-*` interface and is dropped, so nginx answers 502 with no obvious cause.
   The bootstrap allows inbound from the Docker bridge address space (`172.16.0.0/12`) to exactly the ports in
   `compose/processes.json` — not a blanket `allow in on docker0`, because the compose network's bridge is named
   dynamically and a blanket rule outlives the reason for it.

A third, smaller one: **`func start`'s bind address**. nginx can only reach the host port if the function host
listens on all interfaces rather than loopback. Core Tools prints the address it binds at startup; step 16 reads it,
and if it is loopback-only the runner sets `ASPNETCORE_URLS=http://0.0.0.0:<port>` per host. Verified rather than
assumed, because it is one line either way and a wrong assumption here looks identical to defect 2.

### Running Loady on Linux

`backend/backend.ps1` is Windows-only in the parts that matter — `taskkill`, `Start-Process` into new windows, and
the Cosmos DB Emulator `.exe`. It is not modified. `scripts/ld-dev.sh` is the Linux equivalent and reads
`compose/processes.json`, which lists each function host, its port and its build output directory:

| Function | Port | Started by default |
|---|---|---|
| `Loady.Backend.Api` | 7160 | yes |
| `Loady.Events.Api` | 7296 | yes |
| `Loady.Backoffice.Api` | 7001 | yes |
| `Loady.Loady2Go.Api` | 7152 | yes |
| `Loady.Loady2Share.Api` | 7094 | yes |
| `Loady.Public.Api` | 7247 | `--public` |
| `Loady.Public.BusinessPartners.Api` | 7248 | `--public` |
| `Loady.Public.Lanes.Api` | 7249 | `--public` |
| `Loady.Public.Products.Api` | 7250 | `--public` |
| `Loady.Public.LoadingPoints.Api` | 7253 | `--public` |
| `Loady.Public.UnloadingPoints.Api` | 7254 | `--public` |

This is exactly the set `backend.ps1` starts. `Loady.Reports.Api` and `Loady.Imports.Api` exist under `src/Domains/`
and are deliberately excluded — `backend.ps1` does not start them and `Loady.Imports.Api` has no
`local.settings.json`, so it has no local configuration to start with.

Each host starts detached with `setsid func start --no-build --port <port>` from its `bin/Debug/net10.0` directory,
pid and log under `~/.local/state/loady-vm/run/<name>.{pid,log}`, so `ld-stop` and `ld-logs` address them by name
instead of killing every `func` on the machine. `AZURE_FUNCTIONS_ENVIRONMENT` and `EnvironmentName` are `Localhost`
in the profile, as `backend.ps1` sets them.

**The compose file is this repository's own**, at `compose/loady-vm.yaml`, standalone rather than an override layered
on `loady-one/backend/compose.yaml`. It carries the five services the Mac file has (redis, azurite, apim, sqlserver,
cosmosdb) plus `extra_hosts` on `apim`, healthchecks on sqlserver and cosmosdb that `ld-start` waits on instead of
sleeping, and named volumes. It bind-mounts `nginx.conf` from the `loady-one` checkout read-only. The tradeoff is
drift: when the team changes `backend/compose.yaml`, this file does not follow. Mitigated cheaply — `ld-reset` diffs
the service names, images and published ports of the two files and prints a warning when they disagree. A warning,
not a failure: a deliberate difference is the normal case here.

**The Cosmos emulator serves HTTPS with a self-signed certificate.** On Windows and macOS the installer puts it in
the trust store; in a container on Linux nothing does, and every .NET client fails the handshake before the first
document. The bootstrap fetches `https://localhost:8081/_explorer/emulator.pem` once the container is healthy and
installs it into `/usr/local/share/ca-certificates`, then runs `update-ca-certificates`. The well-known emulator key
in `local.settings.json` is unchanged and needs nothing.

tracked script from this repository, so both machines run the same code. The four existing `ld-*` aliases in the
Mac's `~/.zshrc` are deleted as part of this work — they point at `~/Repositories/loady/loady-one`, a path that no
longer exists, so all four are currently broken.

| `ld-tfin` | loads `.tf-vars` from Bitwarden, then `terraform init` | Mac |

No command in this set commits, pushes, merges or opens a pull request, and none is added later (rule 2). `ld-stn`
creates a local branch, which is the one git write the rule permits: it publishes nothing and it is what makes a
worktree possible at all.

### Parallel streams

Worktrees work here and are worth having. `ld-stn LOADY-15234-tender-notifications` branches off `origin/dev` and
creates `~/loady-worktrees/LOADY-15234-tender-notifications`; `ld-stl` lists them; `ld-str` retires one. The branch
name is validated against what the remote actually contains — `LOADY-<digits>` optionally behind `feature/`,
`bugfix/` or `chore/`, which covers every branch on the remote today — and `--any` overrides for the rare exception.
The base is `dev`, the repository's default branch.

Three things follow from the machine, and they are the whole design:

1. **`loady-one` stays clean.** `git worktree add` writes its metadata under `.git/worktrees/`, never into the
   working tree, so nothing a teammate pulls changes. Linked worktrees share the main checkout's `.git/info/exclude`,
   so the agent-file exclusions from step 3 cover every worktree automatically; `ld-agents` only has to place the
   symlinks in each new one, which `ld-stn` does as its last act.
2. **Only one stream can run the stack.** Every service in the compose file pins a `container_name` and a host port,
   and the function hosts bind fixed ports — a second `ld-start` collides on all of them. A `loadystack` slot under
   `~/.local/state/loady-vm/` guards it: `ld-start` and `ld-reset` claim it and name the holding worktree on refusal,
   `ld-stop` releases it. A refusal is an answer, not an obstacle to route around — stop the stack in the other
   stream, or do work that does not need it.
3. **The data is shared, the code is not.** Each worktree builds into its own `bin/obj`, so builds, `dotnet test` and
   Rider indexing run in as many streams as wanted. But there is one SQL Server and one Cosmos emulator on the
   machine: a migration applied from one stream is visible to every other, and `ld-reset` wipes the data for all of
   them. Migration work belongs in one stream at a time.

Rider follows the slot: one instance, opened on the worktree that holds it. In any other stream the answer to a
.NET symbol question is `rg` and the build, because Rider's backend is indexing a different branch.

`ld-add`/`ld-update`/`ld-remove` replace the broken aliases and pass the connection string as `-- --connection ...`.
`AppDbContextDesignFactory` reads that argument first and the `loady_relational_database_connection` environment
variable second; passing it explicitly is what makes the commands behave identically in an agent's non-interactive
shell. The variable is also exported from the profile, for `dotnet ef` invoked by hand or by Rider.

### Dotfiles

`dotfiles/` in this repository owns the VM's global agent configuration and its Rider project files, with one
`dotfiles/sync.sh` keeping each tracked file equal to its live counterpart. This replaces the earlier idea of having
`setup.sh` copy the Mac's `~/.claude` across: a copy is unversioned, drifts silently, and has to be repeated after
every rebuild, while a tracked pair is reviewable and survives a destroy.

| Repository file | Live file | Where |
|---|---|---|
| `dotfiles/ai/instructions.md` | `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md` | VM |
| `dotfiles/ai/claude/settings.json` | `~/.claude/settings.json` | VM |
| `dotfiles/ai/codex/config.toml` | `~/.codex/config.toml` | VM |
| `dotfiles/rider/forwardedPorts.xml` | `.idea/.idea.Loady/.idea/forwardedPorts.xml` in the `loady-one` checkout | VM |
| `dotfiles/rider/indexLayout.xml` | `.idea/.idea.Loady/.idea/indexLayout.xml` in the same place | VM |

**The sync runs on the VM only, and that boundary is deliberate.** The Mac's `~/.claude` is already owned and synced
by another repository; a second sync managing the same live file would produce a conflict on every edit, and the
loser would be whichever ran last. The VM has no such owner — it is a machine this repository is the only manager of
— so there is nothing to collide with there. Nothing in `dotfiles/` is ever synced to the Mac. On the VM the trigger
is a crontab line; there is no launchd agent because there is no Mac side.

Either side may be edited — the tracked file or the live file through the app. The last-synced content is kept under
`~/.local/state/loady-vm/dotfiles/`, so a one-sided change is copied across and a two-sided change is a conflict that
writes nothing and names the pair. Writes are temp-and-rename and mode 0600, and the script never runs git: a change
that lands here is a working-tree change for the founder to commit (rule 2).

**`ai/claude/settings.json` is where rule 2 stops being prose.** Claude runs with `--dangerously-skip-permissions`,
so an allow list approves nothing that would have been asked about anyway — but deny rules still bite in that mode.
The file denies `git commit`, `git push`, `git merge`, `git rebase` and branch deletion outright, in both
repositories. An agent that tries is refused by the harness rather than trusted to have read `AGENTS.md`.

**Rider's forwarded ports are the reason this section exists.** In SSH remote-development mode the mapping lives in
the project's `.idea` directory on the VM, which is disposable: it is lost on every rebuild and on every new
worktree, and rebuilding twelve port entries by hand is exactly the chore that stops getting done. Tracking the file
makes the set reproducible. The always-on entries are `8080`, `7000`, `7160` and `7296` plus `1433` and `6379` for
Mac-side database clients; the rest of the port table is added through Rider's Ports tool window when needed, and a
change made there syncs back to the tracked file.

Two practical points, both verified rather than assumed:

- `.idea/` is already ignored in `loady-one` — `backend/.gitignore` line 352 and the founder's global gitignore both
  cover it — so Rider writing there does not violate rule 1 and no `.git/info/exclude` entry is needed.
- The exact directory name is `.idea/.idea.<SolutionName>/.idea/`, which Rider derives from the solution. For
  `backend/Loady.slnx` that should be `.idea.Loady`, but it is confirmed on first connect (step 19) and the manifest
  corrected if it differs, rather than guessed now.

Each new worktree gets its own `.idea`, so `ld-stn` seeds the tracked Rider files into it at creation; the sync
manifest itself tracks the primary checkout only, because a per-worktree manifest would have nothing stable to name.

`dotfiles/rider/README.md` holds the settings `sync.sh` cannot carry because they live in Rider's own configuration
store rather than a project file — starting with **Tools → SSH Agent Forwarding → off**, which is right here for the
same reason it is on the reference machine: the VM has its own keys and must not borrow the Mac's agent.

Out of scope: `e2etests/` (Cypress against deployed environments only — neither config has a local `baseUrl`),
`backoffice/`, `developer-portal/`, `loady2go/`, `loady2share/` and `pipelines/`. They are checked out with the
repository and buildable; no command in this plan targets them.

## Steps

Steps 1-13 build this repository and touch no host. Steps 14-19 create and verify the machine. Committing each
step's work is the founder's (rule 2); the plan assumes it happens between steps and flags the one place the
ordering is load-bearing.

1. **Repository skeleton.** `AGENTS.md` — instruction ownership, the five rules from the Approach with rule 2 and
   rule 3 spelled out as hard prohibitions (no commit, push, branch, merge or pull request by any agent or script;
   no `gh`; a suggested short commit message is the deliverable instead), the plan and result-file convention
   (`plans/YYYY_MM_DD_<name>.md` paired with `<name>_result.md`), and verification expectations. Plus `CLAUDE.md`
   containing only `@AGENTS.md`, `README.md`, and `.gitignore` (`.terraform/`, `*.tfstate*`; `.terraform.lock.hcl`
   and `.tf-vars` stay tracked — the latter holds item ids, not secrets).
   *Why:* every later step needs somewhere to land and a rule for where; rule 2 has to exist before an agent does
   anything here.
   *Verify:* `rg -i 'costfluent'` over the repository returns nothing; `AGENTS.md` states the git prohibition in
   words an agent cannot read as a default to be overridden.

2. **Move the agent instruction files.** `agents/backend/CLAUDE.md` and `agents/infrastructure/CLAUDE.md` from the
   two files under `~/Repositories/kirill/settings/macos/agents/`, with the .NET version corrected.
   *Why:* they exist in one copy, outside version control, in a directory this work retires.
   *Depends on:* 1.
   *Verify:* both present and non-empty; `diff` against the originals shows only the version correction. **The
   originals are not deleted until the founder has committed and pushed this step** — the one ordering in this plan
   that can lose data.

3. **`scripts/link-agent-files.sh`.** Symlinks into `~/loady-one/backend/`, `.git/info/exclude` entries, idempotent,
   refuses to overwrite a real file it did not create, skips a checkout that does not exist. Runs on either machine
   against whatever checkout is there — the VM's, a worktree's, or the Mac's fallback.
   *Why:* this is what keeps the instruction files out of `loady-one`'s working tree, on every machine that has one.
   *Depends on:* 2.
   *Verify:* run twice against a checkout — `git -C ~/loady-one status --porcelain` empty,
   `readlink ~/loady-one/backend/CLAUDE.md` points into `~/loady-vm`, the exclude file gains nothing on the second
   run.

4. **`scripts/loady-shell.zsh`.** Every `ld-*` function from the table, each delegating to a tracked script.
   *Why:* one definition, both machines, no alias that encodes a path.
   *Depends on:* 1.
   *Verify:* `zsh -n` parses it; a fresh shell that sources it defines every documented function; **no helper
   function name begins with an underscore** — an agent's shell snapshot drops those, and every command calling one
   then dies with "command not found", which reads as a broken repository rather than a shell that dropped half the
   file. Grep for `^_` as part of the check.

5. **Choose the Ubuntu image.** Query `packages.microsoft.com/repos/azure-cli/dists/` for the candidate cloud
   image's codename; use that image if present, the current LTS image if not. Record the answer and the date in
   `infra/loady-vm/README.md`.
   *Why:* the codename gates `az`, and discovering that mid-bootstrap wastes a build.
   *Depends on:* 1.
   *Verify:* the chosen codename returns a `Release` file.

6. **`infra/loady-vm/` Terraform root.** `versions.tf` (Terraform ~> 1.16, `bpg/proxmox`, `tailscale/tailscale`),
   `provider.tf`, `variables.tf` with the sizing table's defaults, `main.tf` (image download, VM, single-use
   Tailscale key, a `terraform_data` that removes stale tailnet registrations before create and on destroy, and a
   `terraform_data` that runs the bootstrap over SSH on every apply), `outputs.tf`, `.tf-vars`, local backend.
   *Depends on:* 5.
   *Verify:* `terraform fmt -check` and `terraform validate` pass; `terraform plan` after `ld-tfin` shows exactly the
   VM, the image, the key and the two `terraform_data` resources, and no resource belonging to any other project.

7. **`infra/loady-vm/tailscale-api.sh`.** Deletes exact-hostname `loady-vm` registrations through the Tailscale API
   and confirms the tailnet is clear before returning.
   *Why:* the API is eventually consistent and a node still online re-registers — which is how a rebuilt VM comes
   back as `loady-vm-1` and every `ssh loady-vm-ts` then reaches nothing.
   *Depends on:* 6.
   *Verify:* run with the key loaded while no such device exists — it lists the tailnet's devices and exits 0.

8. **`infra/loady-vm/bootstrap.sh`.** The guest, in the order of the install table, convergent and safe to rerun,
   streaming progress to its caller and to a 0600 log under `~/.local/state/loady-vm/bootstrap/` with a stable
   `latest.log` symlink. Ends with a version table and reboots on a 15-second timer when Ubuntu asks. Includes the
   ufw rule from the defects section — inbound from `172.16.0.0/12` to the ports in `compose/processes.json`, and
   nothing wider — and the per-checkout git identities.
   *Depends on:* 6, and `compose/processes.json` from step 11.
   *Verify:* `shellcheck` and `bash -n` clean; no reference to `gh` anywhere in it; the real test is step 15.

9. **Checkouts and warm-up inside the bootstrap.** Place the GitHub key, pin `github.com`'s host keys from
   `api.github.com/meta` over `curl`, and clone `~/loady-vm`. Place the passphrase-less Azure DevOps key, pin
   `ssh.dev.azure.com`'s host keys against Microsoft's published fingerprints, clone `loady-one` to `~/loady-one`,
   and bind each checkout to its key with `core.sshCommand`. Then `dotnet restore` + `build` the solution,
   `yarn install --frozen-lockfile` in `frontend/`, `docker compose pull`, `ld-agents`, and finally

   as its checkout exists. A checkout with uncommitted work is reported and left alone — never pulled, never
   stashed, never reset.
   *Why:* without `~/loady-vm` on the VM no `ld-*` command exists there, so this is a hard dependency of every later
   step. The warm-up is what makes Rider's first open and the first `ld-start` fast. The hands-off rule for dirty
   checkouts matters more here than in the reference: under rule 2, a dirty tree is the normal state.
   *Depends on:* 8, and step 13 for the sync it calls (guarded, so a bootstrap that predates it does not fail).
   *Verify:* part of step 15 — both checkouts present, `git -C ~/loady-one status` empty on a fresh clone,
   `ld-status` resolves, and `git -C ~/loady-one push` is possible with no agent forwarded from the Mac.

10. **`infra/loady-vm/setup.sh`.** Runs the bootstrap over SSH with the Bitwarden-loaded register, and nothing else.
    *Why:* it carries no files. Everything the VM needs is either in a repository the bootstrap clones or in the
    Bitwarden register it hands over — `dotfiles/` (step 13) took the one job, the agent configuration, that would
    otherwise have been a copy from the Mac. A converge command with no file-copying half is also one that cannot
    silently overwrite something on the VM.
    *Depends on:* 8.
    *Verify:* a run against the built VM re-converges it and reports the bootstrap's outcome; no `--files-only` mode
    exists, because there are no files.

11. **`compose/loady-vm.yaml` and `compose/processes.json`.** The five services with `extra_hosts` on `apim`,

    *Depends on:* 1.
    *Verify:* `docker compose -f compose/loady-vm.yaml config` resolves; the manifest's eleven entries match

## Assumptions

- The Proxmox host, its `root@pam` credential, the `local-zfs` datastore and `vmbr0` are unchanged from how the
  existing workstation VM uses them. `192.168.1.51` and `vm_id` 201 are free — checked against the other root's
  defaults, not the live host, which step 15 does first.
- The same personal tailnet is used; `loady-vm` joins as a member device, so the existing policy that lets the
  founder reach their own devices already covers it.
- `loady-one` builds and runs on Linux amd64. The solution targets `net10.0`, every container is a Linux image
  including the Cosmos emulator's `vnext` build, and the only Windows dependencies found are inside `backend.ps1`,
  which is replaced rather than run.
- The Azure DevOps key at `~/.ssh/loady/id_rsa` is still registered on the profile and RSA is still what Azure
  DevOps accepts. Step 14 proves both before the VM exists.
- `local.settings.json` and `appsettings.Localhost.json` are tracked in `loady-one` (12 and 18 files), so no local
  configuration has to be carried from the Mac. Only `.claude/settings.local.json` is gitignored there, and each
  machine generates its own rather than one being copied to the other.

## Risks

- **The Cosmos emulator `vnext` image is the least predictable dependency.** Slow to start, self-signed, and the one
  service with no track record on Linux in this setup. Mitigated by a healthcheck that `ld-start` waits on rather
  than a sleep, the certificate step, and a named volume so a restart is not a reseed. If it proves unusable the
  fallback is a real Cosmos DB free-tier account — a connection-string change in a local settings override, not a
  redesign.
- **The passphrase-less Azure DevOps key on the VM disk.** It grants push access to the company's monorepo, and it
  is the same identity the Mac holds. Mitigated by the machine's boundaries — no password login, inbound SSH only
  from the LAN and the tailnet, disk on a host the founder owns — and it is the price of headless pushes. Anyone who
  reaches the VM's `dev` user has it; that is the threat model to accept or reject, and it is the same one the
  reference machine already runs under.
- **Rule 2 makes uncommitted work the normal state on the VM**, and the VM is the only copy of it. `ld-tfd` refuses
  while any exists in the checkout **or in any worktree**, the bootstrap never touches a dirty checkout, `ld-str`
  refuses to remove a worktree that holds work, and nothing in this plan stashes or resets. The residual risk is a
  host failure between edits and a push, which no part of this setup can mitigate.
- **Streams share one database.** A migration applied in one stream is live for every other, and `ld-reset` wipes
  the data for all of them. No lock prevents this — the slot guards the running stack, not the schema. Migration
  work in one stream at a time is a discipline, and `docs/remote-development.md` is where it is written down.
- **The standalone compose file drifts from the team's.** Accepted deliberately — it is the only way to add
  `extra_hosts` and healthchecks without touching `loady-one`. Mitigated by mounting their `nginx.conf` rather than
  copying it (the file most likely to change) and by the drift warning in `ld-reset`.
- **Both workstation VMs running at once overcommits the host.** Mitigated in code: `ld-up` refuses and names the
  other VM. It cannot be enforced against a start from the Proxmox web UI.
- **Company source on personal hardware.** The VM holds a full `loady-one` checkout on a home Proxmox host; the disk
  is not encrypted at rest. Accepted by the founder: the company machine has too little CPU and memory to build this
  solution, and the work has to happen somewhere. The compensating controls are the machine's boundaries — no
  password login, inbound SSH only from the LAN and the tailnet, and a host the founder owns.
- **The agent instruction files exist in exactly one copy right now**, outside version control. Step 2 moves them and
  step 19 deletes the originals; the ordering between them is load-bearing and depends on a manual push.
- **The Mac's fallback checkout invites accidental drift.** It is kept on purpose for host outages, and the risk is
  that it quietly becomes a second live workspace: a branch edited in both places, or a stale checkout mistaken for
  current. Mitigated by discipline rather than code — a fallback session starts with a fetch and ends with a push —
  and by the fact that the Mac's toolchain is not maintained for this solution, so it is uncomfortable enough to be
  self-limiting. `docs/remote-development.md` says this in as many words.

## Decisions taken

All five are settled; they are recorded here because each one shapes a step, and a later reader will want the
reason rather than the ruling.

1. **Company source on personal hardware: allowed.** The company machine has too little CPU and memory to build this
   solution. The boundaries in the Risks section are the compensating controls.
2. **Disk: 300 GB**, thin-provisioned.
3. **`ld-up` refuses, with a one-flag override.** `--takeover` shuts the other workstation VM down gracefully, waits
   for it to stop, and then starts this one. Refusing by default protects a build in progress; a single flag keeps
   the common case — switching machines deliberately — from being three manual steps that get routed around.
4. **The Mac keeps `~/loady-one` as a cold fallback** for a Proxmox outage, not as a second workspace. Rule 4 and
   the corresponding risk say what that means in practice.
5. **The Azure DevOps key is copied to the VM with its passphrase removed.** The requirement is git over SSH working
   flawlessly and unattended on the VM, with no web UI; an encrypted key cannot do that, and the existing key is
   already registered on the profile. See Secrets and identities for the full reasoning.
