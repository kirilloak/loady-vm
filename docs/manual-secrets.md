# Manual secrets

What Bitwarden holds for this setup, why each item exists, and how to restore it. Nothing here is
in Git, and nothing here can be regenerated by a system — that is the definition of what belongs
in this file.

`ld-tfin` reads `infra/loady-vm/.tf-vars`, which maps each `TF_VAR_*` to a Bitwarden item id and a
field. That file is tracked because item ids are identifiers, not secrets.

## The three items

| Item | Fields used | Used for |
|---|---|---|
| `dev-infra/dev-proxmox` | login password | `root@pam` on the Proxmox API — creating the VM, and `vm-start`/`vm-stop` |
| `prod-infra/prod-tailscale` | `api_key`, `tailnet` | minting the VM's one-hour member auth key |
| `loady-vm/keys` | `ssh_loady_ado_base64`, `ssh_loady_vm_github_base64`, `ssh_loady_vm_base64` | written onto the VM by the bootstrap, and the Mac's own key to the VM |

The first two already exist and are shared with other work. The third is created by hand, once.

## Creating `loady-vm/keys`

Three keys, each stored as single-line base64 of the private key file. Field names are
`snake_case`; `type: 1` is a hidden custom field.

### 1. The Mac's key to the VM — `ssh_loady_vm_base64`

One key per destination: this one opens the workstation and nothing else. It is stored only as a
backup — cloud-init injects its public half at first boot, so without it and without Tailscale a
lost key is a rebuild.

```bash
ssh-keygen -t ed25519 -f ~/.ssh/loady/loady-vm/id_ed25519 -C loady-vm
ssh-add ~/.ssh/loady/loady-vm/id_ed25519
```

### 2. The Azure DevOps key — `ssh_loady_ado_base64`

**Not a new key.** The existing `~/.ssh/loady/id_rsa` is already registered on the Azure DevOps
profile, and Azure DevOps accepts only RSA for Git over SSH, so a fresh ed25519 key would register
and then fail every push.

What has to change is the passphrase. The key on the Mac is encrypted, and an encrypted key cannot
be used unattended: a headless Rider backend, a tmux session, `ld-vm git push` or anything an agent
runs would each need an `ssh-agent` primed by hand after every reboot. Strip it **on a copy**, and
store the copy:

```bash
cp ~/.ssh/loady/id_rsa /tmp/loady-ado-vm
ssh-keygen -p -N "" -f /tmp/loady-ado-vm      # enter the existing passphrase once
ssh -i /tmp/loady-ado-vm -o IdentitiesOnly=yes -T git@ssh.dev.azure.com   # must authenticate with no prompt
```

The original on the Mac keeps its passphrase, for fallback use. The consequence of reusing one key
for both machines is that revoking it revokes both, which is acceptable because the Mac is a
fallback rather than a daily pusher.

### 3. The GitHub key — `ssh_loady_vm_github_base64`

Its only job is cloning this repository onto the VM, which is a hard dependency of everything after
the bootstrap: without `~/loady-vm` there is no `loady-shell.zsh`, so no `ld-*` command exists.

```bash
ssh-keygen -t ed25519 -f ~/.ssh/loady/github/id_ed25519 -C loady-vm-github
```

Add the public half to the GitHub account (Settings → SSH and GPG keys), then:

```bash
ssh -i ~/.ssh/loady/github/id_ed25519 -o IdentitiesOnly=yes -T git@github.com
```

### Storing them

```bash
export BW_SESSION="$(bw unlock --raw)" && bw sync
id=<the loady-vm/keys item id>

store() {   # store <field name> <private key file>
  bw get item "$id" \
    | jq --arg n "$1" --arg v "$(base64 < "$2" | tr -d '\n')" \
         '.fields = ((.fields // []) | map(select(.name != $n))) + [{name: $n, value: $v, type: 1}]' \
    | bw encode | bw edit item "$id" >/dev/null
}

store ssh_loady_vm_base64        ~/.ssh/loady/loady-vm/id_ed25519
store ssh_loady_ado_base64       /tmp/loady-ado-vm
store ssh_loady_vm_github_base64 ~/.ssh/loady/github/id_ed25519

shred -u /tmp/loady-ado-vm 2>/dev/null || rm -P /tmp/loady-ado-vm
```

Then uncomment the two `loady-vm/keys` lines in `infra/loady-vm/.tf-vars` and put the item id in
them.

### Checking

Every field `.tf-vars` names exists and is non-empty — prints the ones that do not:

```bash
awk '!/^[[:space:]]*(#|$)/ && $3 == "field" { print $2, $4 }' infra/loady-vm/.tf-vars | sort -u \
  | while read -r item field; do
      bw get item "$item" \
        | jq -e --arg f "$field" '.fields[]? | select(.name == $f and (.value | length > 0))' >/dev/null \
        || echo "missing: $field on $item"
    done
```

## Rotating a key

Update the field in Bitwarden, then `ld-tfin && ld-vm-setup` from `infra/loady-vm`. The bootstrap
rewrites the key on the VM only when it differs, 0600.

## The Terraform state

`infra/loady-vm/terraform.tfstate` is local and gitignored. It holds the Proxmox password and a
Tailscale auth key in clear, so it is never committed and never copied anywhere.

Losing it does not lose the VM. Either import the machine:

```bash
cd infra/loady-vm && ld-tfin
terraform import proxmox_virtual_environment_vm.loady_vm pve-2/201
```

or rebuild it, which is the cheaper answer most days — the machine holds nothing that is not in Git
or Bitwarden except unpushed work. Check for that first: `ld-tfd` refuses while any exists.

## Lost access to the VM

The bootstrap joins the tailnet with `--ssh`, so a lost or rotated `loady-vm` key is not a rebuild:
`tailscale ssh dev@loady-vm` from the Mac, replace `~/.ssh/authorized_keys` with the new public
half, done.

Both doors gone at once is a rebuild — the `dev` user has no password, so the Proxmox console
cannot log in — and the disk holds nothing that is not in Git or Bitwarden except unpushed work,
which is why the register keeps `ssh_loady_vm_base64`.
